# AI Workbench — Main Product Vision / Главная цель разработки

AI Workbench — это локальная offline-first multi-agent среда разработки программных проектов.

Цель проекта:
Создать не просто чат с ИИ и не просто генератор планов, а полноценную локальную AI-команду разработки, которая может взять идею пользователя и провести её через полный цикл создания проекта:

idea → analysis → planning → architecture → implementation → testing → review → fixes → repeat → final report / working project.

Главный принцип:
Один ИИ-агент не должен пытаться быть экспертом во всём. Вместо этого в системе должен быть главный Orchestrator, который анализирует проект, определяет нужные роли и назначает специализированных агентов под задачу.

## Основная архитектурная идея

В центре системы находится главный Orchestrator Agent.

Он отвечает за:
- анализ пользовательской идеи;
- определение типа проекта;
- определение технологического стека;
- оценку сложности проекта;
- выбор нужной команды AI-агентов;
- разбиение проекта на этапы;
- назначение задач агентам;
- контроль выполнения;
- запуск тестов;
- анализ ошибок;
- отправку задач на исправление;
- повторный цикл test/fix/review;
- подготовку финального отчёта.

Система должна работать не как один универсальный агент, а как AI-команда:

- Orchestrator Agent — главный координатор;
- Product Manager Agent — требования, user stories, scope;
- Business Analyst Agent — бизнес-логика и сценарии;
- Architect Agent — архитектура проекта;
- API Designer Agent — REST/GraphQL API;
- Backend Agent — серверная часть;
- Frontend Agent — интерфейс;
- Language Specialist Agents — специалисты по конкретным технологиям;
- Database Agent — структура БД и запросы;
- QA Agent — тестирование;
- Code Reviewer Agent — качество кода;
- Security Auditor Agent — безопасность;
- DevOps Agent — запуск, сборка, деплой;
- Technical Writer Agent — README, документация, инструкции;
- Error Detective / Fixer Agent — анализ ошибок и исправления.

## Что система должна уметь в конечном виде

Пользователь описывает проект, например:

"Сделай CRM на React + FastAPI + PostgreSQL"

Система должна:

1. Создать Run.
2. Проанализировать задачу.
3. Определить тип проекта: web app / SaaS / CRM.
4. Определить стек: React, FastAPI, PostgreSQL.
5. Подобрать команду:
   - product-manager
   - architect
   - api-designer
   - frontend-developer
   - react-specialist
   - backend-developer
   - fastapi-developer
   - postgres-pro
   - qa-expert
   - code-reviewer
   - security-auditor
   - technical-writer
6. Объяснить, почему каждый агент выбран.
7. Сформировать product-spec.md.
8. Сформировать architecture.md.
9. Сформировать tasks.md.
10. Создать execution graph / staged steps.
11. Раздать задачи агентам.
12. Дать агентам возможность работать с проектом через tools:
    - list_files
    - read_file
    - search_code
    - propose_patch
    - apply_patch
    - run_tests
    - git_diff
    - git_status
13. Запустить разработку.
14. Запустить тесты.
15. Если тесты падают — передать ошибки Fixer Agent.
16. Исправить ошибки.
17. Повторить цикл test/fix/review.
18. Сформировать финальный отчёт.
19. Показать пользователю diff, статус, что сделано и что осталось.
20. Предложить commit, но не делать опасные действия без контроля.

## Архитектурные паттерны из multi-agent подхода

AI Workbench должен использовать несколько паттернов постепенно.

### 1. Pipeline Pattern

Используется для последовательного процесса:

input → spec → plan → architecture → tasks → implementation → tests → review → final report.

Каждый этап зависит от предыдущего.

### 2. Planning Pattern

Orchestrator должен не просто отвечать на запрос, а строить план и execution graph.

План должен быть структурированным:
- task id
- type
- assigned agent
- dependencies
- expected files
- required tools
- test commands
- status

### 3. Router Pattern

Система должна выбирать нужных агентов и модели под тип задачи.

Примеры:
- React-задача → react-specialist
- FastAPI-задача → fastapi-developer
- SQL-задача → sql-pro / postgres-pro
- ошибка тестов → error-detective / fixer
- безопасность → security-auditor
- деплой → devops-engineer

### 4. Reflection Pattern

После генерации решения должен быть этап проверки.

Пример:
Developer Agent написал код.
Reviewer Agent проверил diff.
QA Agent запустил тесты.
Fixer Agent исправил ошибки.
Цикл повторяется до прохождения проверок или до лимита итераций.

### 5. Tool Use Pattern

Агенты должны не только писать текст, но и использовать инструменты:
- читать файлы;
- искать по коду;
- предлагать patch;
- применять patch;
- запускать тесты;
- смотреть git diff;
- анализировать ошибки.

### 6. Multi-Agent Collaboration

На поздних этапах разные агенты могут совместно решать сложные задачи.
Но сначала общение должно идти через главного Orchestrator, чтобы не создать хаос.

## Важный принцип развития

Нельзя сразу строить хаотичную систему из 50 агентов.

Нужно развивать AI Workbench постепенно:

### Phase 1 — Current foundation

- Runs
- Project Profiles
- Product spec generation
- Plan generation
- Architecture generation
- Task generation
- Staged step execution
- RunDetail timeline
- Dashboard

### Phase 2 — Agent Registry + Team Assignment

Добавить:
- реестр агентов;
- категории агентов;
- skills;
- default tools;
- default model;
- enabled/disabled;
- risk level;
- can_edit_files;
- can_run_commands;
- best_for;
- автоматический выбор команды под проект;
- отображение Assigned Team в RunDetail.

Цель Phase 2:
Orchestrator должен уметь выбрать команду агентов под конкретный проект и объяснить выбор.

На этом этапе агенты ещё не обязаны редактировать файлы.

### Phase 3 — Tools + Patch-based Editing

Добавить инструменты:
- list_files
- read_file
- search_code
- propose_patch
- apply_patch
- git_diff
- git_status

Главный принцип:
Агент не должен бесконтрольно ломать проект.
Сначала он предлагает patch/diff, система применяет его внутри workspace, потом показывает результат.

### Phase 4 — Test/Fix Loop

Добавить цикл:

implement → run tests → analyze errors → fix → run tests again → review.

Нужны лимиты:
- max iterations;
- timeout per command;
- stop on repeated same error;
- error report;
- partial success handling.

### Phase 5 — Role-based Development

Разные агенты начинают выполнять реальные задачи:

- backend agent пишет backend;
- frontend agent пишет UI;
- database agent проектирует БД;
- QA agent пишет и запускает тесты;
- reviewer проверяет diff;
- security agent проверяет риски;
- devops agent готовит запуск.

### Phase 6 — Advanced Multi-Agent Runtime

Только после стабильного single-orchestrator flow можно добавлять:
- параллельное выполнение независимых задач;
- agent-to-agent discussion;
- debate mode;
- multi-review panels;
- automatic replanning;
- production release workflow.

## Safety philosophy

Цель проекта — не ограничить агентов до бесполезного состояния.

Правильный подход:
Не меньше возможностей, а больше контроля над возможностями.

Нужны режимы:

- read-only mode — агент только анализирует;
- patch-only mode — агент предлагает изменения;
- auto-apply inside workspace — агент может менять файлы внутри выбранного проекта;
- approval-required mode — рискованные действия требуют подтверждения;
- hard-block mode — разрушительные действия вне workspace запрещены.

Примеры:
- read_file — safe;
- edit file inside project — allowed in controlled mode;
- run tests — allowed;
- npm install — approval or controlled mode;
- rm -rf, deleting outside workspace, modifying system files — hard block.

## Конечный результат

AI Workbench должен стать локальной AI software company.

Пользователь даёт идею.
Orchestrator собирает команду.
Команда проектирует, пишет, тестирует, проверяет, исправляет и доводит проект до рабочего состояния.

Главная цель:
Сделать систему, которая может медленно, но последовательно вести проект через полный цикл разработки, а не просто генерировать Markdown-планы.
